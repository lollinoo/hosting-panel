# ADR 0021 — Database per Sito e phpMyAdmin: MariaDB Condiviso come Fonte Unica e Forwarder Autenticato

- **Stato:** `APPROVATO — M2`
- **Data:** 2026-11-14
- **Riferimento:** spec `docs/superpowers/specs/2026-11-08-production-hosting-panel-design.md`, `CP-01`, `ADR-0016`, `ADR-0019`, `ADR-0020`
- **Migrazioni:** nessuna (nessuna tabella nel database del pannello; il container condiviso `hp_mariadb` è l'unica fonte di verità)

## 1. Contesto

Ogni sito WordPress gestito dispone già dal provisioning di un database primario e di un utente primario sul server condiviso `hp_mariadb` (`ADR-0016`). Per completare M2 il cliente con permesso `site.databases.manage` deve poter:

1. Creare ed eliminare database aggiuntivi e utenti database aggiuntivi dedicati al sito, ruotarne la password e assegnare o revocare privilegi granulari sui database del sito.
2. Aprire phpMyAdmin direttamente dal pannello già autenticato sul solo perimetro di quel sito, senza esporre porte pubbliche del server database o dell'interfaccia web di amministrazione e senza modificare o riavviare `hp_mariadb` o i container WordPress (`CP-01`).

## 2. Decisioni

### 2.1 MariaDB condiviso come unica fonte di verità (nessuna tabella nel pannello)

- Non viene aggiunta alcuna tabella nel database PostgreSQL del pannello per replicare database, utenti o permessi MySQL/MariaDB.
- `SiteDatabasesRunner` nell'executor legge lo stato reale direttamente da `hp_mariadb` interrogando `information_schema.SCHEMATA` + `information_schema.TABLES` (`DATA_LENGTH + INDEX_LENGTH`), `mysql.user` (`Host = '%'`) e `mysql.db` (`Host = '%'`).
- L'assenza di uno stato speculare nel pannello elimina disallineamenti in caso di database creati o eliminati dal cliente dentro phpMyAdmin: tutte le risorse nello spazio di nomi del sito risultano direttamente dall'istanza MariaDB.

### 2.2 Spazio dei nomi per sito e doppia validazione (prima di SQL e in lettura)

- Il prefisso deterministico del sito è `siteDatabasePrefix(siteId)` = `wp_<sha256(siteId).hex[0..12]>` (usato anche da `siteDatabaseIdentifier` in `SiteProvisioner`), mentre l'account temporaneo di sign-on per phpMyAdmin usa `siteDatabaseSignOnUser(siteId)` = `pma_<sha256(siteId).hex[0..12]>` e non compare mai nelle liste utenti né può essere scelto dal cliente.
- I suffissi inseriti dal cliente devono rispettare `SITE_DATABASE_SUFFIX_PATTERN` (`^[a-z0-9][a-z0-9_]{0,15}$`, 1–16 caratteri; nome completo `wp_<12hex>_<suffisso>` entro 32 caratteri), così ogni identificativo rimane valido e distinto dal database/utente primario `wp_<12hex>`.
- **Prima di raggiungere SQL:** il contratto IPC `SiteDatabasesIpcRequestSchema` (`.strict()`) valida la richiesta con Zod; `parseSiteDatabasesRequest` verifica il prefisso (`assertCheckedSitePrefix`, `assertCheckedSignOnUser`) e chiama `isSiteDatabaseName` sui nomi di database e utente (restituendo `NOT_FOUND` se estranei al prefisso del sito). Inoltre il servizio API `#assertNotProtected` (con conferma sullo schema IPC `SiteDatabaseCustomNameSchema`) vieta la cancellazione del database primario e qualsiasi cancellazione, reset password, grant o revoke sull'utente primario (`400 VALIDATION_ERROR`, `reason: "protected"`), consentendo invece di assegnare a utenti aggiuntivi i privilegi anche sul database primario.
- **In lettura da MariaDB:** `parseSiteDatabasesState` e `buildSiteDatabasesBatch` ri-validano ogni riga restituita con `isSiteDatabaseName` prima di includerla nel DTO o usarla in istruzioni SQL (scartando eventuali nomi non conformi e filtrando `pma_<12hex>`). Il carattere `_` viene eseguito con escape `\_` sia nei pattern `LIKE` di lettura sia negli identificatori `` `<db_esc>`.* `` delle clausole `GRANT` e `REVOKE` (incluso `HP_DB_NAME_ESCAPED` nei job `db.provision` di `apps/docker-executor/src/site-jobs.ts` per i nuovi siti).

### 2.3 Esecuzione SQL come `root` solo dall'executor

- API e frontend Web non parlano mai con MariaDB né con Docker. L'unica strada SQL è `mariadbRootExec` in `apps/docker-executor/src/site-databases.ts`, che esegue `runDockerExec` dentro il container `hp_mariadb` leggendo la password root da `/run/secrets/mariadb-root` e passando le query su `stdin` al client `mariadb --user=root --batch --skip-column-names --raw`.
- Ogni interrogazione e batch antepone `SET SESSION lock_wait_timeout = 30;` e applica limiti espliciti: timeout `15_000 ms` per la lettura dello stato, `45_000 ms` per i batch di mutazione/sign-on, output massimo `MARIADB_MAX_OUTPUT_BYTES` (`1 MiB`), e coda seriale per sito `siteQueues` in `SiteDatabasesRunner` (timeout IPC in `client.ts`: `75_000 ms` CRUD, `120_000 ms` sign-on; timeout BFF in `apps/web`: `20_000 ms` GET, `85_000 ms` mutazioni, `130_000 ms` sign-on).
- Gli errori di `mariadbRootExec` vengono mappati a messaggi fissi (`DOCKER_ENGINE_UNAVAILABLE`, `ALREADY_EXISTS`, `NOT_FOUND`, `RESOURCE_LOCKED`, `INTERNAL_ERROR`) senza esporre `stderr`, SQL, hash o dettagli interni.
- I privilegi concessi agli utenti aggiuntivi e all'account di sign-on sono esattamente i 20 privilegi a livello di database definiti in `MARIADB_DB_PRIVILEGES` (`ALTER`, `ALTER ROUTINE`, `CREATE`, `CREATE ROUTINE`, `CREATE TEMPORARY TABLES`, `CREATE VIEW`, `DELETE`, `DELETE HISTORY`, `DROP`, `EVENT`, `EXECUTE`, `INDEX`, `INSERT`, `LOCK TABLES`, `REFERENCES`, `SELECT`, `SHOW CREATE ROUTINE`, `SHOW VIEW`, `TRIGGER`, `UPDATE`), escludendo `GRANT OPTION` e qualsiasi privilegio globale, con `MAX_USER_CONNECTIONS 5` per ciascun utente aggiuntivo e `MAX_USER_CONNECTIONS 10` per l'account di sign-on (`MAX_USER_CONNECTIONS 40` è applicato all'utente primario in `DB_PROVISION_SCRIPT`).

### 2.4 Password, limiti di quota, budget connessioni, chiusura sessioni e ciclo di vita del sito

- **Password e hash:** le password temporanee (`24` caratteri `[A-Za-z0-9]` via `crypto.randomInt`) sono generate nell'API da `SiteDatabasesService`, mostrate una sola volta nella risposta di creazione utente o reset password (`temporaryPassword`), e mai salvate né loggate. Prima dell'invio IPC all'executor vengono convertite da `mysqlNativePasswordHash` (in `packages/contracts/src/site-databases.ts`) nel digest MariaDB `*<40 hex>` (`MYSQL_NATIVE_PASSWORD_HASH_PATTERN`); solo l'hash attraversa l'IPC ed è passato a MariaDB tramite `IDENTIFIED BY PASSWORD '<hash>'`.
- **Limiti per sito e budget connessioni (`R40`):** massimo `SITE_DATABASES_MAX = 10` database aggiuntivi e `SITE_DATABASE_USERS_MAX = 10` utenti aggiuntivi per sito (esclusi database e utente primari); il superamento restituisce `409 QUOTA_EXCEEDED`. Il server condiviso `hp_mariadb` mantiene `--max-connections=150` (`CP-01`); per singolo sito i limiti `MAX_USER_CONNECTIONS` sono `40` per l'utente primario del sito (impostato da `DB_PROVISION_SCRIPT` durante `db.provision`), `5` per ciascun utente aggiuntivo e `10` per l'account di sign-on `pma_<12hex>`, per un tetto complessivo di `100` connessioni simultanee per sito (`40 + 10 × 5 + 10`). `db.provision` viene eseguito esclusivamente durante il provisioning iniziale del sito (step `create_database` di `site.provision` ed eventuali retry di un setup fallito), mai su `service.deploy`, `service.restart`, `site.domains` o `site.reassign`: un sito creato prima di questa versione riceve il limite `40` solo quando il suo database viene ri-provisionato, e il passaggio una-tantum previsto in `M6` per i siti esistenti imposterà sia il grant escapato sia tale limite.
- **Chiusura delle connessioni aperte:** dopo `ALTER USER` (reset password o rotazione su trasferimento sito), `DROP USER IF EXISTS` (eliminazione utente), `REVOKE ALL PRIVILEGES` (revoca grant), rotazione dell'account di sign-on phpMyAdmin e `dropAll`, l'executor esegue `KILL USER '<user>'@'%'` così le connessioni già aperte con credenziali revocate o ruotate vengono interrotte immediatamente.
- **Cancellazione del sito:** `SiteProvisioner.remove` nello step `drop_database` invoca `executor.siteDatabases({ siteId, op: "dropAll" })` dopo `db.drop` (ignorando `NOT_SUPPORTED` quando il backend è disabilitato). L'operazione `dropAll` individua tutti gli utenti e i database validi conformi al pattern dello spazio di nomi `wp_<12hex>` più `pma_<12hex>` (i nomi fuori pattern vengono saltati), esegue `DROP USER IF EXISTS` e `KILL USER` per ogni utente, e infine esegue `DROP DATABASE IF EXISTS` su tutti i database validi nello spazio di nomi `wp_<12hex>` (incluso il database primario).
- **Trasferimento del sito ad altra organizzazione (`R41`):** in `SiteProvisioner.reassign`, all'inizio dello step `redeploy` (che viene eseguito anche alla ripetizione di un trasferimento interrotto a metà), l'API richiede `list` all'executor e per ogni utente aggiuntivo (`!primary`, escluso l'utente primario del sito) invia `setUserPassword` con l'hash di una nuova password casuale generata e subito scartata (mai loggata né salvata); l'executor chiude le sessioni attive dell'utente con `KILL USER`. Database, utenti aggiuntivi e privilegi restano invariati (il nuovo proprietario imposta una nuova password dal pannello); `NOT_SUPPORTED` viene ignorato come in `remove` per `dropAll`, mentre qualsiasi altro errore fa fallire lo step. L'account `pma_<12hex>` non necessita di intervento al trasferimento perché la sua password esiste solo nel cookie cifrato del pannello e il forwarder ri-verifica permesso e appartenenza organizzazione presso l'API.

### 2.5 phpMyAdmin condiviso su `127.0.0.1`, forwarder autenticato e cookie cifrato

- **Unico contenitore di piattaforma (`hp_phpmyadmin`):** immagine digest-pinned `phpmyadmin@sha256:e4b3eb5305cd42d21512bb55def2bab52625d56df927ad4ee1864a9354c84d40` (`5.2.3-apache`, pre-scaricata da `prewarmSiteImages`), in ascolto esclusivamente su `127.0.0.1:${HP_PHPMYADMIN_PORT:-8306}` (`DEFAULT_PHPMYADMIN_PORT = 8306`, con blocco esplicito delle porte `22`, `80`, `443`, `2222`, `3000`, `4000`, `5432`). **`HP_PHPMYADMIN_PORT` deve avere lo stesso valore in `executor.env` e `web.env`**, altrimenti l'executor e il forwarder web puntano a porte diverse.
- **Hardening del contenitore:** `User: "33:33"`, `ReadonlyRootfs: true`, `Privileged: false`, `CapDrop: ["ALL"]`, `SecurityOpt: ["no-new-privileges:true"]`, `Memory` e `MemorySwap` a `512 MiB`, `MaxRequestWorkers 4` (`4 × 64 MiB = 256 MiB`, entro i tre quarti di `512 MiB`), `PidsLimit: 100`, `NanoCpus: 500_000_000`, `RestartPolicy: unless-stopped`, quattro `tmpfs` dedicati (`/var/run/apache2`, `/sessions`, `/var/www/html/tmp`, `/tmp`), configurazione e parametri MPM prefork montati `:ro` da `/var/lib/hosting-panel/phpmyadmin/config.inc.php` e `/var/lib/hosting-panel/phpmyadmin/hp-mpm.conf` (directory creata da `infra/linux/bootstrap-dedicated.sh`), variabili `UPLOAD_LIMIT=32M`, `MEMORY_LIMIT=64M`, `MAX_EXECUTION_TIME=300` e zero segreti in `Env`.
- **Rete e invarianza `CP-01`:** `ensurePhpMyAdminContainer` crea la rete bridge `hp_pma_net` e vi collega anche `hp_mariadb` con alias `hp-mariadb` senza ricreare né riavviare il server database. Il file `config.inc.php` imposta `auth_type = 'http'`, `MemoryLimit = '0'` (così si applica il `memory_limit` PHP imposto da `MEMORY_LIMIT`), `AllowRoot = false`, `AllowNoPassword = false`, `AllowArbitraryServer = false`, `VersionCheck = false`, `SendErrorReports = 'never'`, `ShowChgPassword = false`, `ShowServerInfo = false`, `UploadDir = ''`, `SaveDir = ''`, `TempDir = '/var/www/html/tmp'`, `blowfish_secret = ''` e deriva `PmaAbsoluteUri` solo da `HTTP_X_FORWARDED_PREFIX` validato (`^/phpmyadmin/[A-Za-z0-9_-]{1,128}/$`).
- **Forwarder e sessione sul pannello:** `apps/web/src/lib/phpmyadmin-forwarder.ts` (esposto dalla route `/phpmyadmin/[siteId]/[[...path]]/route.ts`) è l'unico punto d'ingresso: accetta solo `GET`, `HEAD`, `POST` (`405` sugli altri metodi), valida `siteId` e i segmenti di percorso contro traversal e normalizza la root con `308` sullo `/` finale (`apps/web/next.config.mjs` abilita `skipTrailingSlashRedirect: true` per evitare loop con Next 16), verifica su **ogni richiesta** la sessione `hp_session`, impone `isSameOrigin` sulle richieste non `GET`/`HEAD` (`403`), decifra il cookie JWE `hp_pma` (`dir`/`A256GCM`, `HttpOnly`, `SameSite=Strict`, `Secure` in produzione, `Path=/phpmyadmin/<siteId>/`, `Max-Age=14400`, `aud: "hp-phpmyadmin"`, vincolato a `siteId`, `orgId` e `sid = sha256(csrfToken)[0:32]`) e interroga l'API (`GET /v1/organizations/:orgId/managed-sites/:siteId/databases/phpmyadmin`, con cache TTL `30 s` fino a `1000` voci per `tokenHash:sid:orgId:siteId`) per verificare il diritto attuale sul sito e lo stato pronto prima di inoltrare verso `127.0.0.1`. La chiamata upstream verso phpMyAdmin usa il client dedicato `apps/web/src/lib/phpmyadmin-upstream.ts` (`node:http` e `node:stream`, **senza alcun timeout proprio** (`R50`), invece di `fetch` di Node i cui timeout a `300 s` su header e body libererebbero il posto del sito mentre PHP continua a lavorare). Per evitare che le richieste lente o i reload di un solo sito saturino tutti e `4` i worker di phpMyAdmin (`R49`), ogni istanza del forwarder limita ciascun sito a **`2` richieste simultanee verso upstream** (coda FIFO per sito; attesa superiore a `30 s` -> `503` con pagina dedicata `"busy"` per navigazioni e `503` vuoto altrimenti; le richieste in coda il cui client chiude escono subito senza raggiungere upstream). Ogni posto resta impegnato finché lo scambio reale con phpMyAdmin non termina: la chiusura del client non abortisce phpMyAdmin, e se gli header di risposta superano l'attesa massima del forwarder (`310 s`, esito `detached`) il browser riceve una risposta `503` dedicata (*"phpMyAdmin is still working"* / *"phpMyAdmin sta ancora lavorando"*, pagina HTML sulle navigazioni e `503` vuoto altrimenti) che invita ad attendere o a riaprire phpMyAdmin dalla scheda Database per interrompere l'operazione, mentre lo scambio viene comunque drenato in background fino a EOF prima di liberare il posto (`HEAD`, `204`, `205`, `304`, `401` e redirect rilasciano subito), senza mai rallentare altri siti.
- **Account di sign-on per sito:** alla `POST /api/bff/orgs/[orgId]/managed-sites/[siteId]/databases/phpmyadmin` (protetta da `X-CSRF-Token`, same-origin e `hp_session`), l'API genera una nuova password temporanea, l'executor crea/aggiorna `pma_<12hex>` con `MARIADB_DB_PRIVILEGES` su tutti i database del sito ed esegue `KILL USER`, la BFF cifra le credenziali nel cookie JWE `hp_pma` e restituisce solo `{ data: { url: "/phpmyadmin/<siteId>/" } }`. Il forwarder rimuove cookie del pannello, `Authorization` del client e `X-Forwarded-*`, inietta `Authorization: Basic` per `pma_<12hex>`, `X-Forwarded-Prefix`, `X-Forwarded-Proto`, `Accept-Encoding: identity`, riscrive `Set-Cookie` e `Location` nel prefisso del sito, e su `401` upstream cancella `hp_pma` mostrando la pagina HTML localizzata con link di ritorno alla scheda database.

### 2.6 Capability flag e disponibilità per runtime

- `PlatformCapabilitiesDto` espone `phpMyAdminAvailable: isPhpMyAdminAvailable(runtimeBackend)`, che vale **`true` esclusivamente su `linux-systemd`** (e `false` su `local-simulator` e `disabled`).
- Su `local-simulator`, le operazioni CRUD su database e utenti sono simulate in memoria da `SimulatedSiteDatabases`, mentre le route `/databases/phpmyadmin` restituiscono `422 NOT_SUPPORTED`. Su `disabled`, tutte le operazioni restituiscono `422 NOT_SUPPORTED`. Quando il sito è in stato `deploying` o `maintenance`, creazione di database e utenti, reset password, grant e le route `/databases/phpmyadmin` restituiscono `409 RESOURCE_LOCKED` (`reason: "not_ready"`), mentre la lettura (`list`), l'eliminazione di database/utenti e la revoca dell'accesso (`revoke`) restano consentite (`site-databases.service.ts`).

## 3. Alternative scartate

- **Un contenitore phpMyAdmin per sito:** moltiplicherebbe RAM/processi/riavvii di piattaforma per ogni sito e complicherebbe ciclo di vita e aggiornamento immagine rispetto a un unico contenitore condiviso `hp_phpmyadmin` isolato per credenziali e sessione.
- **Autenticazione nativa `cookie` o script `signon.php` dentro phpMyAdmin:** richiederebbe gestione sessioni PHP condivise o segreti di sign-on nel web container e manterrebbe uno stato locale in phpMyAdmin meno controllabile dell'injection `Authorization: Basic` dal forwarder su rete loopback con verifica sessione e permesso su ogni richiesta.
- **Tabella nel database del pannello per replicare database e utenti MariaDB:** introdurrebbe una doppia fonte di verità destinata a divergere appena il cliente crea o elimina tabelle/database o subisce modifiche fuori dal pannello.
- **Porta pubblica dedicata o hostname dedicato (`db.<panel host>` / `pma.<panel host>`) in questo ciclo:** esporre direttamente una porta pubblica aggirerebbe il forwarder autenticato del pannello, mentre un hostname separato richiederebbe un record DNS e certificazione aggiuntiva non presenti nell'installazione base di M2 (vedi riga 6 di `BLOCKED.md`).

## 4. Conseguenze, limiti noti e rischi accettati

- **Stessa origine del pannello (`/phpmyadmin/<siteId>/`) — *rischio accettato (R35, `BLOCKED.md` riga 6)*:** un'eventuale XSS dentro phpMyAdmin girerebbe sulla stessa origine della UI del pannello. Mitigazioni attive: cookie di sessione e `hp_pma` `HttpOnly` (`SameSite=Strict`), tutte le mutazioni BFF protette da `X-CSRF-Token`, intestazioni anti-framing sulle pagine del pannello (`X-Frame-Options: DENY` e `Content-Security-Policy: frame-ancestors 'none'` su ogni percorso eccetto `/phpmyadmin/…`), mentre le risposte inoltrate di phpMyAdmin mantengono l'eventuale `X-Frame-Options` upstream o ricevono `X-Frame-Options: SAMEORIGIN` con la `Content-Security-Policy` upstream invariata (`R39`), oltre all'immagine phpMyAdmin digest-pinned con `VersionCheck = false` e `SendErrorReports = 'never'`. **Percorso di upgrade:** servire phpMyAdmin su un sottodominio dedicato (`db.<panel host>` o `pma.<panel host>`), che richiede la configurazione di un record DNS dedicato.
- **Memoria condivisa e concorrenza di phpMyAdmin (`R38, R49, R50`) — *rischi accettati*:** un unico contenitore `hp_phpmyadmin` (`MemoryLimit = '0'`, `MEMORY_LIMIT=64M`, `512 MiB` container, `MaxRequestWorkers 4`, cap forwarder di `2` worker per sito con attesa massima `30 s`) serve tutti i clienti senza mai colpire i siti WordPress o `hp_mariadb`. Restano due rischi residui accettati: (1) **due siti distinti** che eseguono ciascuno operazioni lente possono comunque saturare tutti e `4` i worker condivisi e mettere in coda un terzo sito; (2) **phpMyAdmin non impone alcun timeout SQL** (`max_statement_time`), quindi query lente (anche oltre `300 s`, mantenute dal client upstream privo di timeout proprio) occupano i `2` posti del sito finché terminano in MariaDB — dopo `310 s` il forwarder restituisce al cliente la pagina `503` dedicata e il cliente può riaprire phpMyAdmin dalla scheda Database (la rotazione esegue `KILL USER` e termina le query in corso). **Percorso di upgrade:** alzare worker/RAM o separare phpMyAdmin per tenant in fasi successive.
- **Traffico in uscita dalla rete `hp_pma_net` non bloccato (`internal: false`) — *rischio accettato (R35)*:** una rete bridge Docker con `--internal` impedisce il port publishing su `127.0.0.1`, necessario perché il web container raggiunga `hp_phpmyadmin` sul loopback dell'host. **Percorso di upgrade:** aggiungere regole firewall/nftables di egress sul bridge `hp_pma_net` se richiesto da profili più restrittivi.
- **Limite upload `32 MiB` (`UPLOAD_LIMIT=32M`) e timeout lettura HTTP Traefik di `60` secondi — *rischio accettato (R35)*:** importazioni SQL molto grandi o lente possono andare in timeout lato proxy o superare `32 MiB`. **Percorso di upgrade:** usare dump compressi (`.sql.gz` / `.zip`), suddividere il file o introdurre in M4 un flusso guidato di import asincrono.
- **Il cliente può eliminare il database primario del sito da phpMyAdmin — *rischio accettato (R35)*:** `DROP` fa parte di `MARIADB_DB_PRIVILEGES` perché richiesto da diversi aggiornamenti e plugin WordPress, quindi l'account del sito può eseguire `DROP DATABASE` sul proprio database primario da phpMyAdmin; il pannello mostra un avviso esplicito prima dell'apertura. **Percorso di upgrade:** nessuna restrizione a livello MariaDB senza rompere la compatibilità WordPress; la protezione resta il backup (M4).
- **Budget connessioni condiviso (`--max-connections=150`) e siti pre-M2 (`R35, R30, R40`):** anche con i limiti per sito (`40` primario, `5` utenti extra, `10` sign-on; max `100` per sito), due siti molto attivi insieme possono comunque esaurire le `150` connessioni totali del server condiviso. Inoltre i siti creati prima di questa versione mantengono sia il vecchio grant non escapato su `wp_<hex>` sia l'utente primario senza cap finché il database non viene ri-provisionato. **Percorso di upgrade:** un passaggio una-tantum nell'updater futuro (`M6`) sui siti esistenti imposterà sia il grant escapato (revocando il precedente) sia `MAX_USER_CONNECTIONS 40`.
- **Credenziali dopo trasferimento sito, rimozione membro o sospensione organizzazione (`R41`):** il trasferimento ad altra organizzazione ruota gli utenti database aggiuntivi, ma perimetro escluso da M2 (risalente alla creazione del sito e rimandato all'audit `M6`): la password database WordPress propria del sito non viene modificata dal trasferimento. Inoltre un membro rimosso dall'organizzazione o un'organizzazione sospesa conservano password database ancora funzionanti, utilizzabili solo dall'interno di un sito sullo stesso server (non risolto in M2).
- **Altri limiti operativi dai report:** eventuali nomi sotto il prefisso del sito che non rispettano le regole di naming (`SITE_DATABASE_NAME_PATTERN` / `SITE_DATABASE_CUSTOM_NAME_PATTERN`, creabili solo come `root` perché nessun utente del sito ha `CREATE` globale) vengono saltati da `parseSiteDatabasesState`: non compaiono nella lista del pannello, non contano nella quota di 10 e non vengono rimossi da `dropAll`; il salvataggio multi-grant lato UI esegue chiamate `PUT`/`DELETE` sequenziali (un errore intermedio segnala salvataggio parziale e ricarica lo stato); l'eventuale timeout di `45 s` dell'executor lascia al massimo `lock_wait_timeout = 30` a limitare i blocchi lato server e l'API restituisce `503` (la UI ricarica la lista); riaprire phpMyAdmin ruota la password di `pma_<12hex>` ed esegue `KILL USER`, terminando la precedente sessione phpMyAdmin aperta sullo stesso sito; `SiteDatabasesRunner` serializza le mutazioni per sito in memoria nel singolo processo executor/API previsto dall'architettura single-host.

## 5. Conformità alle regole architetturali

- **Docker socket solo nell'executor:** solo `apps/docker-executor` esegue `runDockerExec` su `hp_mariadb` e gestisce `hp_phpmyadmin` / `hp_pma_net`; API e web comunicano via IPC firmato o BFF/API.
- **Invarianza `CP-01`:** né `hp_mariadb` né alcun container WordPress o Traefik viene mai ricreato o riavviato dalle operazioni su database, utenti, grant, sign-on phpMyAdmin o avvio/verifica di `hp_phpmyadmin` (l'aggancio di `hp_mariadb` a `hp_pma_net` avviene via network connect senza restart).
- **Nessun segreto persistito o esposto:** le password temporanee non entrano nei log, nei DTO di lettura, negli eventi audit o nelle righe DB del pannello (`FORBIDDEN_PUBLIC_DTO_KEYS` vieta `password` e `passwordHash`); l'hash `*<40 hex>` esiste solo nel transito IPC e dentro i dati account di MariaDB; la password temporanea di sign-on viaggia solo nel cookie cifrato JWE `hp_pma` (`HttpOnly`, `SameSite=Strict`) verso il forwarder.
- **Isolamento multi-tenant (`404`):** i siti appartenenti ad altre organizzazioni o i nomi privi del prefisso `wp_<12hex>` del sito restituiscono `404 NOT_FOUND`; il forwarder converte anche `403`/`404` dell'endpoint di verifica permessi in `404`.
- **Audit obbligatorio:** ogni mutazione (`site.database.create`, `site.database.delete`, `site.database.user.create`, `site.database.user.delete`, `site.database.user.password_reset`, `site.database.grant`, `site.database.revoke`, `site.database.phpmyadmin.open`) registra un evento audit senza credenziali; la sola lettura di stato (`GET /databases`) e il controllo permessi per richiesta (`GET /databases/phpmyadmin`) non producono righe di audit.
