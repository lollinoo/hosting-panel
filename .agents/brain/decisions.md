## Phase 1 Settled `/grill-me` Design Decisions (`HCP-SPEC-002` — 2026-11-07)

1. **Clean-Room Docker-Native Baseline (`Q1`, `Q3`, `Q5`)**:
   - Eliminate all external third-party orchestrator adapters, simulation servers, legacy environment variables, and POC tables.
   - Recreate the monorepo cleanly around the canonical `HCP-SPEC-002` domain model with a single SQL baseline (`0001_phase1_docker_native.sql`).
   - Retain dual-mode local persistence (`@electric-sql/pglite` embedded + `pg` external pool) and local `jose` OIDC dev issuer so deterministic tests and local UI workflows run without requiring a live Linux Docker daemon.

2. **Strict Separation of Authority Roles (`Q2` — `HCP-SPEC-002` §4.1–4.2, `AC-F1-03`)**:
   - Define four explicit role tiers:
     - `infrastructure_admin`: Host lifecycle, Linux maintenance, security posture, Docker Engine status, allocations, operations & audit read (`host.*`, `allocation.*`, `template.read`, `quota.read`, `operation.read`, `audit.read`). No implicit unrestricted customer secret/data access without policy/audit.
     - `hosting_admin`: Service templates, allocations, tenant sites/services/quotas within installation/assigned scopes (`host.read`, `host.metrics.read`, `host.docker.read`, `allocation.*`, `template.*`, `site.*`, `service.*`, `quota.*`, `operation.read`, `audit.read`), **strictly denied** `host.maintenance.*`, `host.security.*`, and `host.docker.engine.manage` (`AC-F1-03`).
     - `customer_owner`: Organization-scoped management of own sites, services, stack revisions, quotas read, operations read, and organization members (`AC-F1-02`, `AC-F1-04`).
     - `customer_collaborator`: Least-privilege collaborator governed by explicit `ResourceGrant` / scoped bindings (ABAC + deny precedence).

3. **Explicit 8-Package Monorepo Boundaries (`Q6` — `HCP-SPEC-002` §9)**:
   - `@hosting-panel/config`, `@hosting-panel/contracts`, `@hosting-panel/authz`, `@hosting-panel/hosting-domain`, `@hosting-panel/policy-engine`, `@hosting-panel/executor-contracts`, `@hosting-panel/host-agent-contracts`, `@hosting-panel/database`.
   - In Phase 1, `executor-contracts` and `host-agent-contracts` exposed strictly typed internal interfaces (`ApprovedServiceSpec`, `DockerExecutorPort`, `HostAgentPort`) with disabled stubs returning `NOT_SUPPORTED`.

4. **Phase 1 API Surface & `shadcn@4.23.0` Italian UI (`Q4`, `Q7`, `Q8` — `AC-F1-10`)**:
   - Approved UI dependencies added to workspace: `shadcn@4.23.0`, `radix-ui@1.8.1`, `class-variance-authority@0.7.1`, `clsx@2.1.1`, `tailwind-merge@3.7.0`, `tw-animate-css@1.4.0`.
   - Built three distinct authority consoles (`Infrastructure Admin`, `Hosting Admin`, `Customer Workspace`) with `shadcn` components over the encrypted `HttpOnly` JWE BFF boundary.

## Phase 2 Settled `/grill-me` Design Decisions (`HCP-SPEC-003` — 2026-11-07)

1. **Scope & Deliverable Boundary (`Q1`)**:
   - Author the normative specification `docs/architecture/hcp-spec-003-phase-2.md`, close `ADR-010`, and implement the full Phase 2 runtime inside the monorepo (`apps/docker-executor`, `apps/host-agent`, authenticated IPC, Outbox/Reconciler, minimal `Dedicated` ingress proxy, `systemd` units, Linux bootstrap/break-glass scripts, and `AC-F1-08` outage harness), while initially keeping `Shared Hosting`, `ADR-011`, `ACME/TLS` (later enabled in `ADR-0017`), `SFTP` (later enabled in `ADR-0020`), and production `Backups` (later enabled in `ADR-0022`) closed/gated (`Shared Hosting` remains gated).

2. **Split-Agent Process Topology & Toolchain (`Q2` — Closing `ADR-010` Part 1)**:
   - Enforce three separate privilege domains (`hp-api`/`hp-web`, `hp-docker-executor`, `hp-host-agent`) deployed as independent `systemd` services.
   - Implement `apps/docker-executor` and `apps/host-agent` as lightweight standalone Node.js 24 + TypeScript daemons (zero NestJS, zero new external dependencies), directly sharing `@hosting-panel/contracts`, `@hosting-panel/executor-contracts`, `@hosting-panel/host-agent-contracts`, and `zod`.

3. **Authenticated Local IPC Channel (`Q3` — Closing `ADR-010` Part 2 + `ADR-008` Readiness)**:
   - Use Unix Domain Sockets (`/run/hosting-panel/executor.sock` and `/run/hosting-panel/host-agent.sock`, directory `0750`, socket `0660` confined to group `hp-ipc`, zero open TCP ports) combined with per-request cryptographic signing (`node:crypto` HMAC-SHA256 / Ed25519 over method, path, timestamp, nonce, and SHA-256 body digest, with ±30s clock-skew check and anti-replay nonce cache).
   - Retain portable Named Pipe / ephemeral loopback transport fallback for isolated test suites and non-Linux dev runs.

4. **Docker Engine Boundary & Zero-Sock Data Plane Ingress (`Q4` — `TH-02`, `TH-04`, `CP-01`)**:
   - Confine `/var/run/docker.sock` access exclusively to `hp-docker-executor` via a native `node:http` Docker Engine API (`v1.45+`) client enforcing `Privileged: false`, `CapDrop: ["ALL"]`, `no-new-privileges:true`, `PidsLimit`, CPU/RAM cgroup v2 limits, and isolated per-site bridge networks (`hp_site_<siteId>_net`).
   - Run **Traefik v3 with a read-only Dynamic File Provider** (`/var/lib/hosting-panel/ingress/dynamic:ro`, `watch: true`, `restart: unless-stopped`, **zero `docker.sock` mount**) for atomic hot-reloaded domain routing and 100% Data Plane survival during Control Plane outages (`CP-01`).

5. **Zero-Root Linux Privilege Model & `systemd` Hardening (`Q5` — `TH-03`, `ADR-006`)**:
   - Zero services run as `root`: provision dedicated `/usr/sbin/nologin` system users (`hp-web`, `hp-api`, `hp-executor`, `hp-agent`) and group `hp-ipc`.
   - Mask `/var/run/docker.sock` from Control Plane processes (`InaccessiblePaths=/var/run/docker.sock`) with empty `CapabilityBoundingSet=`.
   - Grant `hp-host-agent` only `AmbientCapabilities=CAP_NET_ADMIN CAP_DAC_READ_SEARCH` with `NoNewPrivileges=yes`, `ProtectSystem=strict`, `SystemCallFilter=@system-service`, and strict `execFile` execution on fixed binary paths without shell invocation (`ALLOWLISTED_HOST_MAINTENANCE_ACTIONS` + static `nftables` `22/80/443` posture checks).

6. **PostgreSQL Transactional Outbox, `unknown` Recovery & Observe-Only Drift Reconciler (`Q6` — `TH-08`, `TH-10`)**:
   - Use PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` for the Transactional Outbox Worker (compatible with both `pg` and `PGlite`, zero mandatory Redis/BullMQ dependency), returning `202 Accepted` (`AsyncAcceptedEnvelope`) and enforcing active operation locks (`409 CONFLICT`).
   - Recover interrupted mutations via the `unknown` state using read-only `getObservedState` inspection (never blind `POST` replay).
   - Keep the Drift Reconciler strictly **observe-only** (`in_sync` / `drifted` + `audit_event`, zero autonomous container restarts or recreations).

7. **Target Linux OS & Live Execution of `AC-F1-08` on Dedicated Linux Environment (`Q7`)**:
   - Standardize on **Ubuntu 24.04 LTS / Debian 12** (`systemd`, `cgroups v2`, `nftables`, Docker Engine CE).
   - Deliver `infra/systemd/*.service`, `infra/linux/bootstrap-dedicated.sh`, break-glass CLI, and `infra/linux/run-outage-ac-f1-08.mjs`, and **execute `AC-F1-08` (`T0..T5` with `SIGKILL` on Web/API/Worker + DB stop under HTTP load) live on the dedicated Linux environment**, recording real measurements in `docs/security/ac-f1-08-execution-report.md`.

8. **Additive Phase 2 DB Migration & `AES-256-GCM` `tmpfs` Secrets (`Q8` — `F1-012`)**:
   - Add non-destructive migration `0002_phase2_runtime_and_secrets.sql` (`encrypted_secrets` encrypted at rest with `AES-256-GCM`, agent heartbeats, and partial unique index on active operation `lock_key`).
   - Mount resolved secrets JIT as read-only files (`0444 :ro` inside `0700`-confined per-service directories for `CapDrop: ["ALL"]` non-root UID compatibility) on `tmpfs` (`/run/hosting-panel/secrets/<serviceId>/<ref>`, Docker `*_FILE` pattern) so plaintext secrets never appear in `stack_revisions`, `outbox_events`, `Config.Env` (`docker inspect`), DTOs, or logs.

9. **Dynamic `PlatformCapabilitiesDto` & Truthful 3-Console `shadcn@4.23.0` Unlock (`Q9` — `AC-F1-10`)**:
   - Evolve `PlatformCapabilitiesDto` to expose `phase: "phase-1" | "phase-2"` and `runtimeBackend: "linux-systemd" | "local-simulator" | "disabled"`, keeping `sharedHostingEnabled` strictly `false` (while `acmeTlsRuntimeAvailable` was later unlocked on `linux-systemd` per `ADR-0017`, `sftpAvailable` was unlocked on `linux-systemd` per `ADR-0020`, `phpMyAdminAvailable` was unlocked on `linux-systemd` per `ADR-0021`, and `productionBackupRuntimeAvailable` was unlocked on `linux-systemd` per `ADR-0022`).

## Production Hosting Panel Owner Decisions (2026-11-08)

Source: `docs/superpowers/specs/2026-11-08-production-hosting-panel-design.md`.

1. **Two product roles**: server administrator (`users.platform_role='infrastructure_admin'`, TOTP 2FA mandatory) and customer hosting admin (`customer_owner` membership).
2. **One customer per server**: the panel runs on a dedicated server for a single hosting customer.
3. **No mail hosting**: no mailboxes. Outgoing mail of sites goes through an SMTP relay configured by the admin.
4. **Languages**: UI in Italian (default) and English, per-user language.
5. **Site-first UI**: customer shell centred on the site (top-bar switcher, tabs), Coolify-like look.
6. **DNS stays at the registrar**: the panel checks DNS, never hosts zones.
7. **Backups**: S3 target configured by the admin.
8. **SFTP and web file manager are mandatory**; databases with phpMyAdmin.
9. **Container terminal only**: no host terminal in the panel. Since M5c (`ADR-0027`) the terminal is a text shell in a site's container, as `33:33`, for the server administrator only: one per session, behind a fresh TOTP code at every open, recorded (who, which site, when, how long, how it ended) without what is typed or printed.
10. **Delivery order** (steps 1–6): 1 foundation (auth, roles, i18n, shell, installer); 2 sites, domains, TLS, outgoing mail; 3 backups; 4 files, databases, site import (first go-live line is steps 1–4); 5 WordPress tools; 6 admin console completion. Each step has its own plan and passes the four sensors plus a real-server check.

## Step 2c Outgoing Mail Owner Decisions (2026-11-09)

Source: `docs/architecture/adr/0018-outgoing-mail-relay.md`.

1. **Sender**: `noreply@<sender domain>`, with the site name and `Reply-To` kept.
2. **Send failures** are visible to the server administrator only.
3. **Panel password-reset emails** are deferred to Step 6.
4. **No per-site SPF/DKIM**: the customer sees "nothing to set up"; the admin page hints SPF/DKIM for the single sender domain.
5. **A site's own SMTP plugin wins**: ours is a default mu-plugin at `PHP_INT_MIN`.
6. **Verified TLS** to the provider: the host must be a hostname, not an IP.
7. **Pre-0.5.0 sites** are redeployed once automatically on update; sites whose service is stopped are upgraded after they are started again.
8. **Limits**: 200 messages/h per site, 100 recipients, 25 MiB. A newsletter needs an external service.
9. **`CP-01` exception**: after a reboot with the panel down, mail is queued, not delivered, until the API is back and re-applies the password (it lives only in tmpfs).
10. **Test send timeout** returns `OPERATION_AMBIGUOUS` ("may have been sent").

## M1a/M1b File Manager & Site SFTP Decisions (2026-11-14)

Sources: `docs/architecture/adr/0019-site-file-manager.md`, `docs/architecture/adr/0020-site-sftp.md`.

1. **Web File Manager (`ADR-0019`)**: isolated per-site `hp_files_<id>` helper container (`network=none`, read-only rootfs, 512 KiB base64 chunks, 2 GiB file cap, async 202 zip/unzip, protected `wp-content/mu-plugins/hp-mail.php`).
2. **Site SFTP (`ADR-0020`, `sftpAvailable: true` on `linux-systemd`)**: single shared digest-pinned `hp_sftp` container (`linuxserver/openssh-server`, port TCP `2222` / `HP_SFTP_PORT`, isolated `hp_sftp_net` bridge) serving chrooted site volumes (`/srv/sftp/<siteId>/files`, UID/GID `33:33`).
3. **Auth & isolation**: password-only SFTP (no SSH keys in cycle 2, no shell, no forwarding); `sha512Crypt` lives in `apps/api/src/sites/sha512-crypt.ts` (`@hosting-panel/contracts` stays browser-safe). Passwords shown once; only `$6$` hashes are persisted (`site_sftp_users`, migration `0008`) and pushed over IPC.
4. **In-place user files & selective recreate**: bind-mounted `passwd`/`group`/`shadow` rewritten in place (`r+` + `ftruncate`) per login without restarting `hp_sftp`; container recreates only when the active site-volume set, image, port, or `sshd_config` changes (`1–3 s` session drop, never touching site containers per `CP-01`).
5. **Compensation, convergence & deletion**: DB writes roll back on executor failure/timeout (`503 DOCKER_ENGINE_UNAVAILABLE`), converged by `HP_SFTP_RETRY_INTERVAL_MS` (`60_000` ms default on `linux-systemd`); `SiteProvisioner.remove` calls `removeSite` before `deleteService`/`purgeSite`.
6. **No firewall rule change**: Docker-published port `2222` traverses DNAT/`FORWARD` bypassing `nftables` `input` and `ufw`; only `bootstrap-dedicated.sh` (`/var/lib/hosting-panel/sftp`, `0700` `hp-executor`) and `install.sh` texts change. Zero new npm dependencies.

## M2 Site Databases & phpMyAdmin Decisions (2026-11-14)

Source: `docs/architecture/adr/0021-site-databases.md`.

1. **Shared MariaDB as sole source of truth (`ADR-0021`)**: zero new PostgreSQL tables/migrations; `SiteDatabasesRunner` queries `hp_mariadb` (`information_schema.SCHEMATA`/`TABLES`, `mysql.user`, `mysql.db`) as root via `runDockerExec` (`mariadb` CLI reading `/run/secrets/mariadb-root`, SQL on stdin, `lock_wait_timeout = 30`, `15 s` state / `45 s` batch timeout, per-site serial queue `siteQueues`, no API-side `list`-before-`create`).
2. **Site namespace & double validation**: deterministic `wp_<12hex>` prefix (`siteDatabasePrefix`) and `pma_<12hex>` sign-on account (`siteDatabaseSignOnUser`), suffix `^[a-z0-9][a-z0-9_]{0,15}$`, cap of `10` custom databases and `10` custom users per site (`409 QUOTA_EXCEEDED`), primary DB/user protected (`400 VALIDATION_ERROR`, `reason: "protected"`). Names are validated before SQL (`SiteDatabasesIpcRequestSchema`, `isSiteDatabaseName`) and re-validated when read back (`parseSiteDatabasesState`, `buildSiteDatabasesBatch`), with `_` escaped (`\_`) in `LIKE` and `` `<db_esc>`.* `` (plus `HP_DB_NAME_ESCAPED` in `db.provision` for new sites).
3. **Passwords, connection budget, termination & deletion**: API generates 24-char passwords (`temporaryPassword`, shown once, never persisted/logged) and sends only `*<40hex>` hashes (`mysqlNativePasswordHash` in `@hosting-panel/contracts`) over IPC. Shared `hp_mariadb` keeps `--max-connections=150` (`CP-01`), with per-site `MAX_USER_CONNECTIONS` caps of `40` (primary user via initial `db.provision`), `5` (each extra user), and `10` (sign-on account) — up to `100` connections per site. `KILL USER` runs after password reset, extra-user rotation on site move (`SiteProvisioner.reassign` step `redeploy`), delete user, revoke, phpMyAdmin sign-on rotation, and `SiteProvisioner.remove` (`dropAll` after `db.drop` on valid pattern-matching names).
4. **Shared `hp_phpmyadmin` + authenticated forwarder (`phpMyAdminAvailable: true` on `linux-systemd`)**: single digest-pinned `phpmyadmin@sha256:...` (`5.2.3-apache`) container bound only to `127.0.0.1:${HP_PHPMYADMIN_PORT:-8306}` (`HP_PHPMYADMIN_PORT` must match across `executor.env` and `web.env`; port `2222` also refused), `User: "33:33"`, `ReadonlyRootfs: true`, `CapDrop: ["ALL"]`, `Memory=512 MiB`, `MemorySwap=512 MiB`, `MaxRequestWorkers 4` (`hp-mpm.conf` mounted `:ro` alongside `config.inc.php`), `MEMORY_LIMIT=64M`, `$cfg['MemoryLimit'] = '0'`, `hp_pma_net` attached to `hp_mariadb` without restarting MariaDB (`CP-01`). Reached only via `/phpmyadmin/<siteId>/` (`next.config.mjs` sets `skipTrailingSlashRedirect: true` and anti-framing `X-Frame-Options: DENY` + `Content-Security-Policy: frame-ancestors 'none'` outside `/phpmyadmin/...`; forwarded phpMyAdmin keeps upstream `X-Frame-Options` or falls back to `SAMEORIGIN` with upstream CSP unchanged) checking `hp_session`, `hp_pma` JWE (`dir`/`A256GCM`, `HttpOnly`, `SameSite=Strict`, `4h`), and `GET .../databases/phpmyadmin` on every request (`30 s` cache). Forwarder calls phpMyAdmin via `apps/web/src/lib/phpmyadmin-upstream.ts` (`node:http`/`node:stream`, no timeout of its own (`R50`), replacing Node `fetch`'s 300s headers/body timeouts so long PHP work never releases the slot early) and enforces at most `2` concurrent upstream requests per site (`R49`, FIFO `30 s` queue wait -> localized `503` busy page or empty `503`), keeping each slot until the real phpMyAdmin exchange finishes: client cancel or `310 s` upstream header wait (`detached` -> localized `503` "still working" page instructing the customer to wait or reopen phpMyAdmin from the Database tab, or empty `503` for non-page requests) drains in background without aborting phpMyAdmin; bodyless `HEAD`/`204`/`205`/`304`/`401`/redirects release immediately.
5. **Accepted risks & carry-over**: same-origin `/phpmyadmin/<siteId>/` accepted for M2 (upgrade path: dedicated subdomain `db.<panel host>` / `pma.<panel host>`, needs extra DNS record per `BLOCKED.md` row 6); shared `hp_phpmyadmin` (`4` workers / `512 MiB`) still lets two busy sites saturate all `4` workers, and phpMyAdmin sets no DB statement timeout (`R49`, customer can re-open phpMyAdmin from Database tab to `KILL USER` slow queries); `hp_pma_net` egress not blocked (`internal: false` required for loopback bind); `UPLOAD_LIMIT=32M` / 60s Traefik `readTimeout`; customer can drop primary DB in phpMyAdmin; two active sites can still exhaust MariaDB's 150 connections; removed members/suspended orgs keep working DB passwords usable only from same-server sites; pre-M2 sites keep unescaped `wp_<hex>` grant and uncapped primary user until one-time M6 updater re-grant/cap (and primary WordPress DB password unchanged on move goes to M6 audit). Zero new npm dependencies.

## M3a Site Backups Decisions (2026-11-15)

Source: `docs/architecture/adr/0022-site-backups.md`.

1. **Tooling, pinned image & per-site encrypted S3 repositories (`ADR-0022`, `productionBackupRuntimeAvailable: true` on `linux-systemd`)**: run site backups via ephemeral `restic/restic:0.19.1` containers orchestrated exclusively by `apps/docker-executor` (`docker.sock` stays executor-only), writing one encrypted repository per site under `<prefix>/sites/<siteId>`. Zero new runtime/dev npm dependencies (`restic` speaks S3 natively; allowlist unchanged).
2. **Encryption key lifecycle & secret isolation**: `infra/linux/bootstrap-dedicated.sh` provisions `/etc/hosting-panel/backup.key` once (`64` lowercase hex chars without newline, mode `0440`, owner `root:hp-executor`, never overwritten on updates); `infra/linux/run-dev-docker.mjs` creates a dev key (`0o640`, `HP_BACKUP_KEY_FILE`); `infra/linux/install.sh` carries the bilingual (`IT` + `EN`) `backup.key` data-loss warning inside its 78-column closing box. Keys and S3 credentials never cross IPC in plaintext or appear in `ContainerSpec.Env`, outbox rows, audit logs, or `.env.example` (S3 secret encrypted/decrypted via `secrets-master.key` and staged into job-private `tmpfs`).
3. **Payload, `CP-01` & normalized problems**: each backup captures the site's WordPress files plus one consistent logical MariaDB dump per database of that site without restarting site containers or MariaDB (`CP-01`), mapping failures into the `17` `BACKUP_PROBLEMS` codes (`16` `BACKUP_FAILURE_CLASSES` + `site_busy`).
4. **Long-running async job model, dedicated outbox lane & migration `0009_backups.sql`**: backups run asynchronously (`start -> poll` with renewed executor lease) on a dedicated outbox lane so slow uploads cannot block site lifecycle operations. Migration `0009_backups.sql` stores global backup settings (UTC nightly schedule defaulting to `02:00 UTC`, retention `1–365` days defaulting to `14`, up to `3` retained manual backups) and per-site backup records.
5. **Retention, permissions & M3a boundaries**: panel-driven pruning (`site.backups.prune` system operation) enforces retention under the single permission `site.backups.manage` (`site.backups.create` is an operation kind, not a permission) for customer manual create/list (no cancel in M3a), while keeping up to `3` manual backups and never deleting the newest valid backup of an existing site (`0` valid backups remain only after site deletion/cleanup). Restore, archive download, E11 cooldown, and E12 fixes were subsequently delivered in **M3b** below; panel database backup, admin restore, and lost-server recovery remain deferred to **M3c**, while historical `operations` cleanup and global key audit remain deferred to **M6** in `docs/architecture/adr/0022-site-backups.md`. Live Docker acceptance Part 5 ran for M3a (`accept-m3-backups.mjs`, `12/12` pass, recorded in `docs/security/step-4-acceptance-report.md`), while live acceptance on the owner's dedicated server with a real S3 bucket remains pending. Zero new npm dependencies.

## M3b Restore & Download Decisions (2026-11-15)

Source: `docs/architecture/adr/0022-site-backups.md` (§5).

1. **Isolated staging (`R77`), `.maintenance` gate (`R79`), and atomic swap**: `_rs_fetch` extracts site files into `.hp_rs_<H>/c/files` behind `.htaccess Require all denied` and writes all database dumps plus the `dbs` manifest exclusively to an isolated staging volume `hp_bk_<jobId>` mounted at `/var/tmp` (never in the Apache/PHP site volume). `_rs_prepare` mounts no site volume and pre-checks `DEFINER` entries (`definer_missing`), `_rs_switch` renames tables atomically with `hp_ru_<H>` behind WordPress `.maintenance` (`<?php $upgrading = time(); ?>`), `_rs_files` swaps three directory levels via `mv --exchange -T` (`R81`: creates missing `wp-content/mu-plugins`, keeps `hp-mail.php` untouched), and `_rs_finish` marks the restore `succeeded` only after removing `.maintenance` (`CP-01`: site containers and `hp_mariadb` are never restarted).
2. **All-or-nothing rollback, crash settlement (`E5`/`R82`), and unchanged `sites.status` (`R80`)**: switch/file failures roll back (`switch_undone`) or preserve leftovers when undo cannot complete (`undo_incomplete`); atomic restore notes live on disk at `<HP_BACKUP_WORK_DIR>/restores/<jobId>.json` (`prepare` -> `switch` -> `switched` -> `ended`) so executor startup runs `cleanupOrphanJobs` (keeping volumes with notes) -> `settleRestores()` -> empty `archives/` -> listen (`R82`). **No restore outcome changes `sites.status`**: on `undo_incomplete` the customer repairs the site by running another restore (`lastRestore` survives reloads; admin alert arrives in **M5**), and the next successful restore (or `purgeSite`) removes the leftovers.
3. **E7 address update & 22 `BACKUP_PROBLEMS`**: successful restores run idempotent `wordpress.set-url` (`job_<32hex>_rurl`) using `site_backups.site_url` (`0010_backup_restore.sql`) -> current `wordpressUrl`; failure sets `address_not_updated` while keeping the restore `succeeded`. `BACKUP_PROBLEMS` expands from 17 to 22 (`restore_prepare_failed`, `switch_undone`, `undo_incomplete`, `definer_missing`, `address_not_updated`).
4. **Decrypted single-zip download (`E9`), executor work directory (`HP_BACKUP_WORK_DIR`), and streaming**: `site.backups.download` produces one decrypted zip per site via `restic dump --archive zip` under `/var/lib/hosting-panel/backups` (`0700 hp-executor:hp-executor`, `archives/` subdir; `HP_BACKUP_WORK_DIR`, created by `bootstrap-dedicated.sh` / `run-dev-docker.mjs` / executor startup with zero systemd unit edits), retained at most 60 minutes (cleared on new prepare, retention discard, `purgeSite`, or executor restart), and streamed in 512 KiB base64 chunks through `lib/bff-chunk-stream.ts` (`30 s` IPC / `40 s` BFF chunk timeout, `Cache-Control: no-store`, relative `303` pre-first-byte error redirects).
5. **Shared E11 customer cap (`6/h`), E12 fixes & M3c split**: customer-initiated `site.backups.create`, `site.backups.restore`, and `site.backups.download` share a sliding cap of `6` heavy actions per site per 60 minutes (`409 QUOTA_EXCEEDED`, `retryAt` detail, `Retry-After` header; admins and nightly runs excluded via `idx_operations_resource_submitted`); E12 raises dump space estimate to `2 × Σ sizeBytes + 1 GiB`, maps `errno 28` to `no_space`, and aligns `key_file_missing` remediation text; panel PostgreSQL backup, admin missing-site restore, and lost-server recovery move cleanly to **M3c**. Zero new npm dependencies.

## M3c Panel Copy & Lost-Server Decisions (2026-11-15)

Source: `docs/architecture/adr/0022-site-backups.md` (§4.10, §6).

1. **Keys on stdin (`R110`)**: `hp-restore-panel` copies `HP_S3_ACCESS_KEY_ID` / `HP_S3_SECRET_ACCESS_KEY` into shell variables, unsets them at once and never exports them; the executor's `panel-fetch.js` gets them on stdin from the builtin `printf`, so they are in no argument list, no child environment and no output. The fetch environment holds only `HP_PANEL_DUMP_DIR`.
2. **Marker before `dropdb` (`R111`)**: `/var/lib/hosting-panel/panel-restore.pending` is written right before `dropdb` and removed after `hp-restore-panel.sql` ran; only when it exists is the "0 sites" check skipped, so a run that failed part way can be repeated.
3. **Restore order**: checks that change nothing → fetch → newer-copy check (every `schema_migrations` id in the copy must ship in the release, read with `pg_restore --data-only` without a connection) → stop `hp-web`/`hp-api` → place `secrets-master.key` → marker → drop/create as `postgres`, then `pg_restore --no-owner` from stdin as `hosting_panel` over `127.0.0.1` (R121) → `hp-accounts setup` → `hp-restore-panel.sql` in one transaction → start + health; the site count connects the same way (R123). The SQL runs after `hp-accounts setup` because an older copy lacks newer columns and the SQL ships with the release.
4. **Host values and file layout**: the hostname and IPv4 come from `executor.env` (written by install.sh), not from arguments; a wrapper in `/usr/local/sbin` (`0750 root:root`) runs `restore-panel.sh` of the `current` release, like `hp-update`; the fetched `restore.pgdump`/`restore.key` live in `HP_PANEL_DUMP_DIR` and a trap removes them (the API's start sweep only matches `op_*.dump`).
5. **Exit codes**: `0` restored, `1` a step failed (safe to repeat), `2` refused (bad arguments, not root, bad `backup.key`, sites present, no S3 keys, a copy from a newer panel). "Not root" is `2` here although `update.sh` uses `1`.
6. **Accepted limits (`R116`)**: one-night freshness; the old server must be off first; the panel keep rule counts from the newest copy and never keeps fewer than 3; the newest copy is always the one taken; a stopped site comes back running; extra DB users come back without passwords; installer accounts are replaced and every session ends; no progress while `pg_restore` runs; `panel_dump_tool_missing` without the PG18 client tools; the script's root-only parts are proven with stubs only, a live run is pending.

## M5d Host Firewall, Updates, Packages & Journals Decisions (2026-11-17)

Source: `docs/architecture/adr/0028-host-firewall-and-updates.md` (§2, §4), rulings `R198`, `R199`, `R200`, `R201`, `R202`, `R203`.

1. **Root work without a shell (`R198` 2.1, 2.4)**: `hp-host-agent` stays `hp-agent` with `CAP_NET_ADMIN` and `CAP_DAC_READ_SEARCH` plus the `systemd-journal` group. New error `HOST_JOB_FAILED` (`502`). The executor restart, the panel update and the package upgrade are refused (`409`) while backups, restores, WordPress updates or an import run. End rows are written by `system`.
3. **The firewall (`R198` 2.2, 2.3, 2.9)**: the database is the source (migration `0017_m5d_firewall.sql`: `firewall_open_ports`, `firewall_blocks`); every change, one at a time, sends the whole lists; the API sends them again at start, retrying every 10 s. Blocks: IPv4 down to `/16`, IPv6 down to `/32`, 500 per family, in the `raw` prerouting chain (they also drop answers), after `tcp dport 22 accept` and IPv6 neighbour discovery. New error `FIREWALL_BASE_RULES_NOT_CURRENT` (`409`). `X-HP-Client-Address` is advice, not a boundary. The panel changes the firewall only on a server whose installer loaded the panel's firewall, signed by `/etc/nftables.d/hosting-panel.nft` (`R202` 1.1): elsewhere the state is `unmanaged`, the agent starts no `nft` and a change answers `409` with "The panel firewall is not installed on this server." (`R203` 3.1). The hand-over: SSH on 22, then the installer again over SSH with `--version` and the installed version, without `--skip-firewall`; the panel restarts. `install.sh` refuses an older version than the installed one (exit 2; `HP_INSTALL_ROOT` only in dry runs) (`R203` 2).
4. **Updates without a registry**: the panel compares running images with the pins of the installed release. The release check lives in memory. A panel container moves to its pin with operation kind `panel.container.apply` (the mail relay has no operation); a site with the shipped `service.deploy`; a stopped site is refused.
5. **Packages**: read with `apt-get -s upgrade` (security, distribution, other); the panel installs only what `unattended-upgrade` allows; other packages and the reboot stay over SSH. `install.sh` installs `unattended-upgrades` (`R198` 3.1; its own nightly default on Debian is not verified).
6. **Health and logs**: Health makes one live call, the four services through the agent, bounded to 3 s, `null` on failure (`R198` 7.1). Logs gains seven journals (four services, three jobs), 1–500 lines, not audited.
7. **Accepted limits (ADR 0028 §4)**: the own-address check is advice and skipped without the header; SFTP 2222 not on the safe list and not filtered by the base rules (it goes to a container); moments without lists after a reboot and after "apply base rules"; no periodic firewall pass; the way out over SSH is `sudo nft flush set inet hp_dedicated_filter blocked_v4` (and `blocked_v6`); a failed path unit needs `systemctl reset-failed` over SSH; host jobs and Apply share one lane; site work does not wait for a host job; a repeated mail-relay Apply writes a second audit row; "current" base rules only means the three sets exist; the SSH port is checked once, by the installer; a later `--skip-firewall` install leaves the sign file, and a sign file deleted by hand also reads `unmanaged`; a newer version given to the installer is an update without `hp-update`'s health check and rollback (`R203`); `nft` 1.0.9 of Ubuntu, real systemd and the session across an update not proven here.

Retention never expires by age a copy among the newest `retentionDays` good ones of an existing site; the per-kind count limits stay; a deleted site's copies expire by age.

## HCP-SPEC-004 Manual TLS Certificates & Backup Destinations Decisions (2026-11-21)

Source: `docs/architecture/adr/0031-manual-tls-certificates.md` (§2, §3, §4), `docs/architecture/adr/0032-backup-targets.md` (§2, §3, §4, §5), HCP-SPEC-004; the engineering run's binding resolutions R1–R7 (`local_root`, accept-script ownership, `tlsVersionId`, capability flags, `partial`, PFX and `.zip.age` blocked).

1. **A certificate is an organisation resource with immutable versions (`ADR-0031` §2.1, §2.4)**: `tls_certificates` and `tls_certificate_versions` (migration `0021_manual_tls_certificates.sql`); a domain has `cert_mode` `acme` (default) | `manual` and a composite foreign key to a version of the same organisation, so another tenant's certificate can never be attached. The private key is AES-256-GCM with AAD `<org>:*:tls:<cert>:<version>`, `key_version` `v1`; leaf and chain are public and stay in clear. Hard delete, no `deleted_at`: the versions cascade and no key ciphertext stays.
2. **PEM only; PFX stays blocked (`ADR-0031` §2.2)**: Node has no PKCS#12 parser and a parser dependency or external tool is not approved (zero-new-dependency rule). The UI never shows PFX; `TLS-14` is `BLOCKED` until the owner approves a pinned parser.
3. **Validation with `node:crypto` and `node:tls` only (§2.3)**: `checkHost` with `subject: "never"` and `partialWildcards: false` (a wildcard covers one level, never the apex), the CN must be among the SANs, IP SANs are refused, serverAuth when an EKU is present, RSA 2048–8192 or EC P-256/P-384, 24 h margin, chain proved by a loopback handshake against the bundled Mozilla anchors (injectable only from a test constructor, never from environment or option). Every error is a `ControlPlaneError` with a fixed `details[].reason` and fixed text, never a value or a parser message; a gate of 2 validations per server and 1 per organisation.
4. **No new proxy bind, no `CP-01` outage (§2.5, §2.15, §3)**: files go to `<dynamic>/manual-certs/<versionId>/{fullchain,privkey}.pem` under the `:ro` dynamic directory the proxy already mounts (`0700` dir, `0400` files, executor uid = proxy uid), the manifest `hp-manual-certificates.yml` holds file references only, `hp-update` sees no payload change and does not recreate the proxy. Rejected: a dedicated `/etc/traefik/manual-certs` bind (recreates the proxy), a conditional bind, PEM inline in YAML, keys only in tmpfs (lost at reboot), editing `acme.json` hot.
5. **Deterministic certificate selection (§2.7)**: Traefik takes the highest sorted SAN key (ties random), so a pure planner in `packages/contracts/src/tls-sni.ts` (`planManualCertificates`, `findManualCaptures`) refuses what it cannot make win (`manual_overlap`, `captures_host`, `acme_eviction_required`); the executor re-runs it against the real `acme.json`. Letting Let's Encrypt and a manual certificate tie on the same key is never published hot: it takes an administrator-confirmed cold cleanup (proxy stopped, `acme.json` backed up, entries removed, proxy started). A loaded manual wildcard blocks sibling ACME orders, so a new ACME sibling under it is refused or created directly on the manual version (`tlsVersionId` on domain create, R4). A version becomes active only after proof (§2.7): a real `tls.connect` through the proxy showing the expected fingerprint (250 ms polling, two consecutive hits, at most 20 s). Back to Let's Encrypt reverses it: routes with `certResolver` first, then publish without the version, then proof the fingerprint is gone.
6. **One operation, the site lock, idempotency by payload (§2.8)**: `site.tls.apply` under `site:<siteId>` (`RESOURCE_LOCKED`), at most one TLS change per site and two non-terminal per server (`RATE_LIMITED`); import is synchronous (`201`, version `pending`, `Idempotency-Key` required); `operations.request_hash` makes the same key with another payload `IDEMPOTENCY_CONFLICT`. The reconciler never orders or rewrites a manual domain (§2.9). A shared certificate rotates across all same-organisation sites in one operation with a per-site permission check and audit.
7. **Permission and tenancy (§2.10–§2.12)**: new permission `site.certificates.manage` (customer owner, administrator, support access: 14 → 15 keys, `ADR-0025` updated); reads use `site.read`; another organisation's certificate is a generic `404`, a hostname covered by another organisation a generic `DOMAIN_CONFLICT`. A site move with a manual domain is `409 CERTIFICATE_IN_USE`; delete is `409 CERTIFICATE_IN_USE` while a domain uses a version, a version is `applying` or `active`, or a non-terminal operation names it. Audit `site.tls_certificate.import|replace|assign|unassign|delete|apply_failed|expiring|expired` carries ids, fingerprints and fixed codes, never a PEM.
8. **Expiry (§2.13)**: one pure function `certificateExpiryTier` (UTC): informative to 30 days, warning to 14, critical to 7 and at expiry; the alert `manual_certificate_expiring` is computed on read (no event storm); manual domains are excluded from the ACME expiry message.
9. **Accepted TLS limits (`ADR-0031` §4)**: the Traefik tag is mobile and the selection rules are proven on 3.7.19; no OCSP/CRL and no automatic renewal of a bought certificate; the key sits on the host disk, not encrypted at rest; a manual host shows the default certificate between removal and the ACME order; after a forced downgrade manual certificates stay served but not manageable; a host reboot and a commercial certificate are owner items.
10. **Destinations are rows, history is never rewritten (`ADR-0032` §2.1, §2.2)**: `backup_targets` (`s3` | `local`), `backup_policies` (`default_site` holds hour, retention and the nightly cursor; `panel`; `site`), `backup_policy_targets` (at most two, priority 1..2), `site_backup_copies` and `panel_backup_copies` (migration `0022_backup_targets_and_copies.sql`). The S3 secret of the old settings is **not** copied or re-encrypted (a ciphertext does not decrypt under another AAD): the `legacy_settings` target keeps reading the frozen `backup_settings` row through `getBackupTarget()`; new S3 secrets use AAD `platform:*:HP_BACKUP_TARGET_S3_SECRET:<targetId>`. Backfill is idempotent (`ON CONFLICT DO NOTHING`, deterministic `md5` ids); a trigger on `backup_settings` keeps the legacy key in step; a boot repair re-attaches copies an older release wrote after a rollback. Executor S3 requests stay byte-identical to the frozen pins.
11. **The local root comes only from the executor (`ADR-0032` §2.3, R1)**: `HP_BACKUP_LOCAL_ROOT` (default `/var/lib/hosting-panel/local-repos`) in the unit file; the API and the customer never send a path, `RESTIC_REPOSITORY` is never taken from a client; the `local_root` column is written only from executor answers, for display. Paths `<root>/<targetId>/{sites/<siteId>,panel}`; marker `.hp-local-target`; `local-target-guard.ts` before every job that mounts a repository (`O_NOFOLLOW` per segment, realpath/dev/ino, free space, write probe because restic hangs on a read-only filesystem); the repository is attached with `HostConfig.Mounts` (refuses a missing source) and never `Binds` (the daemon would create it as root); the executor never creates `<root>/<targetId>` by itself (an unmounted external disk must not fill the system disk) and the unit has no `RequiresMountsFor=` (an absent disk would stop the whole panel). The local branch has no AWS preflight, no credentials file, only `RESTIC_PASSWORD`.
12. **Group-shared `2770` repositories (`ADR-0032` §2.4, §5)**: site jobs stay `33:33` with the executor's gid as `GroupAdd`; the zip export, every panel step and the local probe run as the executor user; right after `restic init` the creator runs `chmod -R g+rwX,o=` on the children (self-healing on the next step). Proven on Docker with restic 0.19.1; `33` without the group and a stranger uid get "permission denied". Recorded divergence from the spec's `0700`: the mode is `2770`, no access for others.
13. **One operation per logical backup, copies in sequence (`ADR-0032` §2.6, §2.7)**: no new operation kind and no way around the hourly caps; the destination is pinned at enqueue on the copy row (a job on a target archived meanwhile ends on the repository it started on); job ids `<opId>` then `<opId>-t2`, retention `-forget`, `-forget-t2`…; recovery asks the executor `status` per non-terminal copy, never `start`. The aggregate is the pure `aggregateBackupStatus`: `running`, `succeeded` (every required copy), `partial` (some but not all), else `failed`; for `site.backups.create` a `partial` closes the operation `succeeded` with the alert `backup_partial`, only `pre_update` treats it as failure. `partial` entered the contracts in M4, with the exhaustive web maps. At most two destinations (`MAX_COPIES = 2`).
14. **Restore, download and retention per copy (`ADR-0032` §2.7)**: restore and download accept an optional strict `targetId` that must name a succeeded copy of that backup, else `404` (no oracle on other targets); the choice is recorded in `restore_target_id` / `archive_target_id`; outbox payloads keep `{siteId, backupId}`. `selectExpired` is unchanged and runs once per target, so "the newest `retentionDays` good copies never expire" holds per target; a `missing` copy loses its row without a `forget`; a logical row is deleted only when no copy remains. A target change deletes no history (`deleteAllSiteBackups` no longer runs on it); `DELETE` of a target archives it and leaves the data.
15. **The customer sees two words (`ADR-0032` §2.5, §2.13)**: "copia esterna" for S3 and "copia su questo server" for local, never `S3`, `bucket`, `endpoint`, `restic` or a path (vocabulary test); the customer (`site.backups.manage`, no new permission) chooses only among `customer_selectable`, enabled, non-archived targets; the local screens always carry the warning that a copy on the same server does not protect from losing the server or the disk and tell to keep an off-server copy and the recovery key.
16. **Disaster recovery from a local repository (`ADR-0032` §2.10)**: `hp-restore-panel --local-repo <dir>` (CLI only, `<dir>` is the panel repository on the remounted disk), `panel-fetch` exits 7 and 8, and `infra/linux/hp-restore-panel.sql` resets the panel ledgers in the same transaction. A single `backup.key` serves every repository and must be kept off the server (`BKP-16`, `BKP-17`); there is no master-key rotation.
17. **Update, rollback and downgrade (`ADR-0032` §2.12, `ADR-0031` §2.15)**: nothing is recreated by the update; an automatic rollback of `hp-update` (90 s health window) stays ungated because it happens before feature data can exist and because every column added to an existing table is NULL or has a DEFAULT (`packages/database/test/rollback-compat.test.ts`); an operator-chosen downgrade to a release whose `RELEASE.json` lacks the feature (`manual-tls`, `backup-targets`) is refused by `hp-update` with exit code `8` when the database uses it, failing closed when the check itself cannot run, unless `--allow-feature-loss` (`infra/linux/update.sh`, `panel_features_in_use` in `infra/linux/lib/common.sh`). As built, a feature counts as in use when a domain has `cert_mode = 'manual'` or a non-legacy, non-archived backup target exists; this is narrower than `ADR-0032` §2.12, which also counts an archived target holding a succeeded copy (that copy stays unreachable for the old release without a refusal). After a forced downgrade the old release does not see local copies and its endpoint change calls `deleteAllSiteBackups` again.
18. **`.zip.age` is blocked, not built (`ADR-0032` §2.11)**: the project forbids a new tool or image without approval and a hand-written `age` is forbidden by the spec. Recommended option for the owner: an `age` image pinned by digest run as a `_age` step after `_zip`, `NetworkMode: "none"`, recipient validated `^age1[02-9ac-hj-np-z]{58}$` (`invalid_recipient`). Until approved `encryptedBackupExportAvailable` stays `false`, the UI does not offer it and a request for `format: "zip.age"` is refused `422 NOT_SUPPORTED`; the contract schema is in place.
19. **Capability flags follow shipping (R5)**: `manualTlsCertificatesAvailable` (M2) and `localBackupTargetsAvailable` (M3) flipped to `true` on `linux-systemd` only by the milestone that shipped them, after the real-Traefik and real-Docker acceptance scripts passed; `encryptedBackupExportAvailable` stays `false`. The acceptance report marks owner-only runs `PENDING (owner)` and the PFX and `.zip.age` rows `BLOCKED`.
20. **Accepted backup limits (`ADR-0032` §4)**: a local copy shares the server's fate; space is checked before a job, not during it (`no_space`); one non-archived local destination (more disks by mounting one volume on the root); a dump per copy, so two copies can differ by seconds; retention and hour are global; a deleted or archived target's data stays for the administrator to remove; mount propagation into the executor's `ProtectSystem=strict` namespace and the root-only read-only and full-disk cases are owner items.

## Per-Customer Site Limit & Site Templates Decisions (2026-11-21)

Source: `docs/architecture/adr/0034-per-customer-site-limit.md`, `docs/architecture/adr/0033-site-templates.md`, issue #33, the swarm run's `GOAL.md` assumptions and lead decisions (`ARCHITECTURE.md`).

1. **`max_sites` NULL means unlimited; the limit binds under the row lock (`ADR-0034`)**: migration `0023_organization_site_limit.sql` adds a nullable `organizations.max_sites` (`CHECK >= 0`), so every existing customer keeps today's behaviour and an automatic rollback works. The binding check runs under the organisation row lock on site creation and on the background move to another organisation (`moveSiteToOrganizationTransactional`); the check at queue time is advisory (early `409`). A refusal reuses `QUOTA_EXCEEDED` (`409`, one `details` entry, no new error code); lowering the limit below usage deletes nothing and only blocks new sites. The limit change is audited.
2. **"Servers" means site/service types on the same dedicated host (`GOAL.md`)**: not a multi-host cluster; the runtime stays single-host `Dedicated` and `Shared Hosting` stays gated (`409 SHARED_MODE_GATED`).
3. **Zero new dependencies: an in-house YAML subset (`ADR-0033`)**: no YAML parser is on the allowlist, so `packages/contracts/src/site-templates/yaml-subset.ts` reads a strict Compose-like subset with error positions (line, column, path); the dependency allowlist is unchanged.
4. **Templates are admin-only and validated by the policy engine (`ADR-0033`)**: only a server administrator creates, versions, enables, disables or archives a template; every source passes `validateSiteTemplateSource` (module policies: no privileged, host binds, `docker.sock`, `cap_add`, host network/pid/ipc or host ports, official image repository pinned by a three-component tag (a digest is refused, `IMAGE_DIGEST_NOT_ALLOWED`, because it cannot follow `php_version`), limits within the ceilings, only declared named volumes, allowed interpolation) on each save and again when a template is enabled, a site is created from it or a site is moved; customers only pick among enabled templates and fill the parameters marked for them.
5. **Versions are immutable; a legacy site is the built-in v1**: `site_template_versions` rows never change or disappear (trigger `trg_prevent_site_template_versions_mutation`); a change is a new version. `sites.template_version_id` `NULL` means built-in WordPress v1 (`stv_wordpress_1` of `stpl_wordpress`), so existing sites and the frozen ADR 0029 pin tests are byte-identical; new sites always store the version id. The built-in source uses `${HP_MODULE_IMAGE}`, resolved to the code pin, so v1 never goes stale.
6. **The built-in starts enabled, an admin-created template starts disabled**: an administrator reviews a new template before customers see it (`ck_site_templates_enabled_needs_default`: no enabled template without a default version; an archived one is disabled; the built-in cannot be archived).
7. **Creation without `templateId` while the built-in is disabled is `404`**: reason `template_unavailable`, for customers and administrators alike, so "disable" is never bypassed; an administrator who names a disabled, non-archived template may use it.
8. **A site moves only to a newer version of its own template**: `POST /v1/admin/sites/:siteId/template-version` refuses another template's version (`other_template`), the same version (`already_current`) and an older one (`not_newer`); no rollback is offered. A retried `Idempotency-Key` replays the first operation before any of these refusals. The move is an explicit administrator action through the existing operation lane, never automatic.
9. **`HP_SITE_DOMAIN` and `HP_SITE_URL` are fixed at render time**: the magic variables (`HP_SITE_ID`, `HP_SITE_DOMAIN`, `HP_SITE_URL`, `HP_MODULE_IMAGE`) take their values when the revision is rendered; a later domain change does not rewrite a stored revision.
10. **Per-site PHP settings travel in the approved spec**: closed-key `configuration.phpIni` becomes `ApprovedServiceSpec.phpIni` (absent = pins unchanged); the executor writes one ini file per service under `/var/lib/hosting-panel/site-php` and binds it `:ro` at `/usr/local/etc/php/conf.d/zz-hp-site.ini`; the executor never receives a path or an ini key outside the closed set, and `phpIni` never reaches the container environment.
11. **Downgrade gate `site-templates`**: `hp-update` refuses (exit code `8`) a downgrade to a release without the feature while a site uses a template version other than `stv_wordpress_1`, unless `--allow-feature-loss`; an older release would replace a custom image by the WordPress pin on a PHP change and forget the stored parameters. The exit-8 hint tells the operator to delete or re-create those sites on built-in version 1 or keep the current release (no route moves a site back or to another template). An automatic rollback stays ungated (migrations `0023` and `0024` are additive).
